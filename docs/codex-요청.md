# Codex 요청서

Claude Code가 Codex에게 남기는 요청. Codex는 작업을 시작할 때 이 파일을 먼저 읽고, **열림** 요청을 처리한 뒤 그 요청의 "처리 결과"만 채운다.
요청 본문은 고치지 않는다. 판단이 필요한 건 처리 결과에 질문으로 남긴다.

## 요청 1 — 2·3층 글 검수 반영 · 닫힘 (main 병합 33f12db)

보낸 날: 2026-10-20 · 대상: `story` 브랜치 커밋 `d1df346`

### 먼저
`git merge main`. main에 바뀐 것:

- **데이터 검사에 "예문에 낱말이 그대로 있어야 함"이 추가됐다.** 병합하면 `bee-2`, `bee-3`에서 `npm test`가 실패한다. 아래 2번을 고치면 통과한다.
- 안개가 남아 있는 동안 질문·보기·카드 문구 속 그 낱말도 화면에서 `▒▒`로 가린다.

### 고칠 것
1. **`bee-3`의 잠긴 낱말 "서식지"가 정의 문장 안에 있다.** "이처럼 동물이나 식물이 살아가는 곳을 서식지라고 한다."는 낱말을 가려도 같은 문장이 뜻을 말해 준다. 그러면 안개 걷기의 단서 찾기가 의미 없고, 정작 이 문장을 고르면 실패한다. 정의 문장이 아니게 바꾸고(예: "이런 곳들이 꽃가루받이 동물의 서식지다."), 뜻을 짐작하게 하는 **다른** 문장을 `clues`로 둔다.
2. **예문을 미리 가려 쓰지 않는다.** `bee-2` `'물을 ○○해 줘.'`, `bee-3` `'생물의 ○○○야.'` → 낱말을 그대로 쓴다(`공급해`, `서식지야`). 가리는 건 화면이 한다. 기본 팩(`pack-5-6.ts`)과 같은 방식.
3. **`bee-3` 연결 질문 문구가 가린 낱말에 기대고 있다.** "서식지를 지키는 일이…"는 안개가 남아 있으면 "▒▒를 지키는 일이…"로 보여 뜻이 통하지 않는다. 잠긴 낱말 없이도 읽히게 바꾼다(예: "동물들이 살아갈 곳을 지키는 일이…").
4. **`bee-3` author 질문의 오답 셋이 상식만으로 걸러진다.** "살던 곳을 줄이고", "꽃을 없애고", "모두 맡겨 보자"는 글을 안 읽어도 틀린 걸 안다. 글을 읽어야 가를 수 있는 그럴듯한 오답으로 바꾼다(예: 꿀벌 먹이만 챙기기, 꽃의 수만 늘리기처럼 일부만 맞는 말).

### 하지 않을 것 (사용자가 정할 일)
- 근거 허용 조합 방식(정확히 일치 vs 필수+허용) — 지금 규칙대로 둔다.
- 설정집 확인 목록(적 이름, "나", 데이터 칸).

### 끝나면
`npm test`, `npm run build` 통과 → `story`에 커밋(`M8: …`) → 아래 처리 결과를 채운다.

## 요청 2 — 2·3층 질문 6개 근거 재검토 · 닫힘 (main 병합)

보낸 날: 2026-10-20

### 배경
사용자가 1층 연결 질문에서 문제를 찾았다. "꿀벌이 줄면 왜 밥상이 위협받을까?"에 정답 근거로 **질문을 되풀이한 5번 문장**("꿀벌이 계속 줄어들면 사람의 밥상도 함께 위협받게 된다")을 요구했고, 그럴듯한 다른 근거(1번 "꿀벌이 열매가 맺히도록 돕는다")는 약타였다. 그래서 규칙을 바꿨다.
- 근거는 **문항마다 정해진 개수(`count`)만큼** 고른다. 화면이 "근거 문장 N개를 골라 봐"로 알려 주고 N개까지만 고를 수 있다.
- 판정: 정확히 `count`개 + `required` 후보 하나를 다 포함 + 고른 문장이 모두 관련 문장(`required` 전체 ∪ `allowed`) 안.
- 출제 원칙은 `docs/작업지시서.md` **1-5**. 1층은 Claude Code가 이미 고쳤다(연결: `count: 2, required: [[1]], allowed: [0, 2]`).

**지금 `bee-2`, `bee-3`의 `evidence`는 Claude Code가 형식만 맞춘 임시값이다.** 내용은 검토하지 않았다.

### 먼저
`git merge main`.

### 할 일
1. `bee-2`, `bee-3`의 질문 6개마다 1-5 원칙으로 `count`, `required`, `allowed`를 다시 정한다.
   - 질문에 이미 쓰인 전제·결과를 되풀이한 문장을 근거로 요구하지 않는지
   - 5~6학년이 그럴듯하게 고를 다른 근거가 약타가 되지 않는지
   - `count`가 "답하는 데 꼭 필요한 문장 수"인지 (`literal` 1, `connect` 2 이상)
2. 근거가 애매해서 데이터로 해결이 안 되면 **질문·보기·본문 문장을 고쳐도 된다**(원칙 4). 고쳤으면 `docs/스토리.md` 7장 출처 메모도 맞춘다.
3. 보기는 지금처럼 글을 읽어야 가를 수 있게 유지한다.

### 하지 않을 것
- `bee-1`, 엔진·화면 코드, 다른 문서.

### 끝나면
`npm test`, `npm run build` 통과 → `story`에 커밋(`M8: …`) → 아래 처리 결과에 **문항별 표**를 채운다.

## [요청5] 3층 헛소문 반박 데이터 · 닫힘 (main 병합, Claude가 모범 반박 2개 추가)

새 카드 **헛소문 반박**을 시험한다(사용자 결정 2026-10-21, 3층부터). 헛소문 여우가 소문 한 문장을 퍼뜨리면, 학생은 본문에서 근거 문장을 고르고 한두 문장으로 반박을 쓴다.
- 판정: 근거 O + 반박 개념 O = 정타, 근거만 O = 약타, 근거 X = 실패. 반박 글은 요약 채점기(핵심 개념 + 의미 + 반대 앵커)를 그대로 쓴다.
- 소문이 살아 있는 동안 적의 공격 +2. 반박에 성공하면 소문이 부적에 묶이고 큰 피해. 엔진·화면은 Claude가 만든다.
- 데이터 형식은 이미 들어가 있다: `src/content/types.ts`의 `Rumor`, `Passage.rumor?`, 검사는 `validate.ts`.

### 먼저
`git merge main` → `AGENTS.md`, `docs/작업지시서.md` 1-5(출제 원칙)와 2-2(요약 채점), `docs/스토리.md` 3·4장, `src/content/passages/bee-1.ts`의 `summary`(개념·앵커 쓰는 법 예시)를 읽는다.

### 할 일 — `src/content/passages/bee-3.ts`에 `rumor` 추가
```ts
rumor: {
  claim: '…',                       // 여우의 말투(반말) 한 문장. 40자 안팎
  evidence: { count, required, allowed? },
  rebuttal: { models, concepts, minConcepts, conceptLabels, rejects },
}
```
1. **claim**: 그럴듯하지만 **3층 본문만 읽으면 반박할 수 있는** 생각 하나. 예(사용자 제안, 1층용): "벌은 꿀만 만들잖아. 난 꿀 안 먹으니까 벌이 없어져도 상관없어!" 3층 본문(야생벌·나비·생활 공간)에 맞게 새로 쓴다.
   - 실제 사람·집단을 겨냥하거나 비웃지 않는다. 본문 문장을 그대로 뒤집은 문장도 아니다(검사가 본문 포함 여부를 확인함).
   - 정답을 암시하는 낱말(본문 핵심 낱말 그대로)을 소문에 넣지 않는다.
2. **evidence**: 소문을 **직접** 반박하는 문장만. 출제 원칙 5·6과 같이 정답 근거는 본문의 절반 미만, `count`는 1 또는 2.
3. **rebuttal**
   - `models`: 모범 반박 4~5개. 5·6학년이 실제로 쓸 법한 말투로, 길이·표현을 다양하게(“아니야, …”, “…때문에 틀렸어”, 근거 문장을 풀어 쓴 것).
   - `concepts`: 꼭 들어가야 할 생각 **2묶음**, 묶음마다 동의어를 넉넉히(띄어쓰기 무시로 비교함). `minConcepts: 2`.
   - `conceptLabels`: 빠졌을 때 학생에게 보여 줄 말(반말, 정답을 그대로 말하지 않는 힌트형).
   - `rejects`: 소문에 **동의하는** 답, 엉뚱한 결론 3~5개. 겉모양이 모범 반박과 비슷해야 거름망 역할을 한다(CLAUDE.md "채점에서 이미 알아낸 것" 참고).
4. **채점 시험 답안**: 처리 결과에 학생 답 예시 **20개**(통과해야 할 10개 + 떨어져야 할 10개)를 표로. 떨어져야 할 것에는 소문에 동의, 근거 없이 감정만, 본문과 무관, 개념 하나만 있는 답을 섞는다. Claude가 이 표로 실제 채점기를 돌려 본다.
5. 1·2층용 소문 후보를 각 1개씩 처리 결과에 글로만 제안한다(데이터에는 넣지 않음). 1층 후보에는 사용자 예시를 다듬어 넣는다.

### B. 기준 만들기 (새 그림 그리지 않음 → 끝나면 멈추고 사용자 확인)

**B1. 에셋 대장 `docs/design/에셋-대장.md`** — 게임에 들어가는(또는 들어갈) 그림을 한 줄에 하나씩.

| ID | 장면(화면 번호) | 자리(보드 번호) | 파일·프레임 | 논리 크기 × 배율 = 화면 크기 | 언제 보이나(상태·사건) | 움직임(B4 기호) | 판 | 상태 | 사용자 메모 |
|---|---|---|---|---|---|---|---|---|---|

- ID 규칙: `CH-`(주인공) `EN-`(적) `BG-`(배경) `UI-`(아이콘·카드 표식) `FX-`(연출) `KEY-`(시작·소개 큰 그림). 예: `CH-reader-defend`, `EN-fox-attack`, `FX-seal-pour`, `UI-icon-think`, `BG-floor2`.
- 판: v1, v2… / 상태: 완성 · 초안 · 없음(제안) · 안 씀(이유).
- "언제 보이나"는 실제 코드 기준(예: `usePoses.ts` — 질문 정타·약타 뒤 700ms 적 `flinch`). 코드에서 쓰지 않는 그림(예: `card-frame.png`)은 "안 씀"과 이유.
- 아직 없는 그림은 **제안**으로: 층별 배경(적 그림 뒤 띠 정도, **본문 위에는 배경 금지**), 탑 소개·보상·완료·패배 장면 그림, 안개 걷힘 연출, B4의 몸 동작 프레임. 꼭 필요한 까닭 한 줄과 크기 제안.

**B2. 장면 보드 `docs/design/asset-board.html`** — 사용자가 브라우저로 여는 보드(상대 경로, 새 라이브러리 없음).
- 화면 01~18(명세 D)마다: **실제 게임 캡처**(1280×800, 전투는 390px도) 위에 **번호 상자**로 그림 자리를 표시하고, 옆에 그 번호의 ID·지금 썸네일(정수 확대)·크기·상태.
- 없는 그림은 회색 자리 상자에 ID와 크기만.
- 맨 아래 "모든 그림 한눈에": 시트를 프레임별로 잘라 ID와 함께 격자로(바탕 `#f5eedb`, 2배 이상).
- **움직임 미리보기**(B4): 지금 있는 프레임으로 주인공·적 3종이 B4 규칙대로 움직이는 모습. "움직임 줄이기" 켜기/끄기 단추와, 규칙 층만·불규칙 층만 보기 단추.
- 캡처는 실제 앱을 띄워 일반 흐름으로 찍는다(필요하면 저장 상태를 만들어 층 이동).

**B3. 그림 방향: 도트 느낌을 살린 일러스트 — `docs/design/스타일-기준.png` + 설명**
- 지금 게임용 그림(64×64·6~9색)은 아이콘에 가까운 작은 도트다. 사용자가 원하는 것은 **키 아트 v4처럼 디테일이 살아 있되 도트 느낌이 분명한 일러스트**다.
- 지킬 것: 픽셀 경계가 또렷함(안티에일리어싱·흐림·그라데이션 금지), 정수 배율로만 확대, 캐릭터 그림은 알파 0/255, 잉크색 외곽선(부분적으로 색 외곽선 허용 여부도 제안), 색 계열마다 음영 단계 수 제한.
- 정할 것(후보를 나란히 보여 주고 추천 하나):
  - 캐릭터 논리 크기 후보 2~3개(예: 96×96, 128×128)와 화면 표시 배율 — **390px 전투 화면에서 적·주인공 창에 들어가는지** 캡처 위에 맞춰 본 그림으로.
  - 계열당 음영 단계(예: 3단계 vs 4단계), 캐릭터당 색 수 상한.
  - 디테일 수준: 키 아트 v4와 주인공 앞·뒤 그림에서 잘라 낸 부분을 같은 배율로 놓고 "이만큼"을 표시.
- 스타일 기준 그림은 기존 그림(키 아트 v4, 주인공 컨셉, 현재 스프라이트)에서 잘라 비교로만 만든다. **새로 그리지 않는다.**

**B4. 움직임 원칙 — 대장 아래 "움직임 표"**
사용자 요청: 위아래로 들썩이거나, 보스는 머리를 조금씩 움직이거나. **일정한 부분과 불규칙한 부분을 섞어 자연스럽게.**

| 층 | 무엇 | 기준(제안값, 보드에서 조정) | 누가 만드나 |
|---|---|---|---|
| 규칙 | 숨쉬기 들썩임 | 위아래 1~2 논리 px, 주기 2.4~3.4초, 부드러운 가감속. **캐릭터마다 주기를 다르게**(박자가 서로 맞지 않게), 시작 시점도 엇갈림 | 코드(Claude) — 그림 1장으로 가능 |
| 불규칙 | 짧은 몸 동작 하나 | 3~7초 사이 무작위 간격, 간격·길이에 ±20% 흔들림, **같은 동작 연속 금지**. 예: 눈 깜빡임(가장 자주), 고개 기울임, 꼬리·옷자락 흔들기, 부채 고쳐 쥐기. 보스(여우)는 머리를 천천히 좌우로 살짝 돌리기·귀 쫑긋 | 그림 프레임(Codex, C단계) + 일정은 코드 |
| 사건 | 공격·움찔·방어·가리키기·봉인 | 지금처럼 0.7초 우선. 그동안 불규칙 동작은 멈춤 | 기존 프레임 |

- 읽기를 방해하지 않게: 움직임은 그림 칸 안에서만, 진폭 작게, 번쩍임·빠른 반복 금지. `prefers-reduced-motion: reduce`면 전부 멈추고 첫 프레임.
- 캐릭터마다 **불규칙 동작 목록과 필요한 프레임 수**(예: 깜빡임 2칸, 고개 3칸)를 표로 제안한다. 이 수가 C단계 시트 규격이 된다.
- C단계 `frames.json`에 더할 모양을 제안: 예 `"idle": { "breath": { "amplitude": 2, "periodMs": 2800 } }`, `"accents": [{ "name": "blink", "frames": ["blink1","blink2"], "ms": 160, "weight": 3 }]`.

**B5. 처리 결과에 사용자가 정할 것**: 캐릭터 크기·음영 단계(B3 후보 중), 움직임 기준값(B4), 그릴 그림 우선순위, 배경을 넣을지와 범위, 다시 그릴 후보(호랑이 얼굴 포함).

### C. (사용자 승인 뒤, 이번에는 하지 않음)
승인된 대장·스타일·움직임 기준대로 그린다: 캐릭터 시트(사건 포즈 + 불규칙 동작 프레임 전부) → 배경 → UI·연출. 그림마다 대장의 판·상태를 갱신하고 보드에 전/후를 함께 보인다. 사용자는 `docs/design/수정요청.md`에 "ID: 고칠 점"으로 적거나 채팅으로 ID를 짚는다. 화면 연결과 움직임 일정 코드는 Claude가 한다.

### 하지 않을 것
- 새 그림 그리기(B는 기존 그림·캡처·잘라 낸 비교만), 게임 화면의 움직임 코드(`src/` 안 — 보드의 미리보기는 `docs/design/` 안에서만), 전투 화면·엔진·채점·콘텐츠 데이터, 스프라이트 파일 수정, 새 라이브러리.

### 끝나면
`npm test`, `npm run build` 통과 → `story`에 커밋(`M12: …`) → 처리 결과에 A의 바뀐 파일·이미지 용량(전/후), B의 대장 행 수(완성·초안·제안별), 보드 여는 법, B5의 정할 것을 채운다. **C로 넘어가지 말고 멈춘다.**
